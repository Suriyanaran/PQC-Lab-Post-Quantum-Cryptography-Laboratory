# PQC-Lab Security Architecture & Threat Model

## 1. Threat Model & Adversary Assumptions

PQC-Lab is engineered under an adversarial model accounting for both classical adversaries and future **Cryptanalytically Relevant Quantum Computers (CRQCs)**.

### Adversary Classes:

1. **Harvest Now, Decrypt Later (HNDL)**:
   - Adversaries record encrypted network traffic today and store it indefinitely.
   - Once a large-scale quantum computer is constructed, the adversary uses Shor's algorithm to compute the private keys and decrypt past conversations.
   - *Mitigation*: The asymmetric key exchange relies on **NIST FIPS 203 ML-KEM**, whose hardness stems from the Module Learning With Errors (M-LWE) lattice problem, for which no efficient quantum algorithm is known.

2. **Active Network Adversary (Man-in-the-Middle / Chosen-Ciphertext)**:
   - The adversary intercepts, alters, reorders, or replays packets on the wire.
   - *Mitigation*: IND-CCA2 security in ML-KEM decapsulation via the Fujisaki-Okamoto transform; strict AEAD authentication tags (`AES-256-GCM` / `ChaCha20-Poly1305`) over payloads and Associated Data (AAD).

3. **Compromised Ephemeral Server Memory**:
   - The adversary dumps server memory after a session has ended.
   - *Mitigation*: **Strict Forward Secrecy**. The server private decapsulation key ($dk$) is zeroized immediately upon completion of the handshake.

## 2. Quantum Threat Analysis

### Shor's Algorithm
- **Mechanism**: Solves the hidden subgroup problem over abelian groups in polynomial time ($\mathcal{O}((\log N)^3)$).
- **Vulnerable Algorithms**: RSA, DSA, Diffie-Hellman (DH), Elliptic Curve Diffie-Hellman (ECDH, X25519), and ECDSA.
- **Impact**: All classical public-key cryptography collapses once CRQCs scale to sufficient logical qubits.

### Grover's Algorithm
- **Mechanism**: Provides quadratic speedup for brute-force searching an unstructured database of size $N$ ($\mathcal{O}(\sqrt{N})$ operations).
- **Impact on Symmetric Cryptography**: Effectively halves the security margin of symmetric ciphers:
  - **AES-128**: Drops to $2^{64}$ quantum operations $\rightarrow$ **INADEQUATE for long-term quantum security**.
  - **AES-256**: Drops to $2^{128}$ quantum operations $\rightarrow$ **HIGHLY SECURE against quantum search**.
- **PQC-Lab Standard**: All symmetric keys derived in PQC-Lab are **256 bits**, ensuring full 128-bit quantum security under Grover's algorithm.

## 3. NIST FIPS 203 ML-KEM Security Parameter Sets

PQC-Lab supports all three NIST FIPS 203 parameter sets:

| Parameter Set | NIST Security Category | Classical Equivalent | Quantum Hardness | Public Key Size | Ciphertext Size | Recommendation |
| :--- | :---: | :---: | :---: | :---: | :---: | :--- |
| **ML-KEM-512** | Category 1 | AES-128 | $\ge 2^{128}$ gates | 800 Bytes | 768 Bytes | Constrained IoT / low bandwidth |
| **ML-KEM-768** | Category 3 | AES-192 | $\ge 2^{192}$ gates | 1,184 Bytes | 1,088 Bytes | **Recommended Default (General Use)** |
| **ML-KEM-1024** | Category 5 | AES-256 | $\ge 2^{256}$ gates | 1,568 Bytes | 1,568 Bytes | Ultra-high classified / defense |

> [!NOTE]
> **ML-KEM-768** is the recommended default standard by NIST and BSI, offering an optimal balance of robust security (Category 3) and sub-1500-byte packets to prevent IP fragmentation over standard Ethernet MTU (1500 bytes).

## 4. Key Management & Forward Secrecy

### Key Erasure & Memory Zeroization
To mitigate cold-boot and memory-dump attacks:
1. Asymmetric private keys ($dk$) are converted into mutable `bytearray` buffers in Python.
2. Once `complete_handshake()` computes the shared secret, the private key buffer is immediately overwritten in-place with zeros:
   ```python
   def _zeroize(b: Optional[bytearray]):
       if b is not None and isinstance(b, bytearray):
           for i in range(len(b)):
               b[i] = 0
   ```
3. When sessions terminate or expire past their TTL, symmetric encryption keys are similarly overwritten before object destruction.

## 5. AEAD Authentication & Replay Prevention

1. **Nonce Freshness**:
   - Every encrypted message utilizes a fresh, cryptographically secure 96-bit (12-byte) nonce generated by `os.urandom(12)`.
   - The session service tracks previously observed nonces and enforces monotonic sequence numbers.
2. **Context Binding via Associated Data (AAD)**:
   - Protocol headers, session IDs, and message sequence numbers are passed into the AEAD cipher as Associated Data.
   - Any attempt by an adversary to redirect an encrypted ciphertext to a different session or replay an old packet invalidates the 16-byte Poly1305 / GHASH tag and is immediately rejected with HTTP 400.
